> ※ **注意层次**：`image_urls` 是**本函数的入参**（请求体小、不受网关限制）。
> 模型侧 I2I 其实**只认 `images`[base64]**，函数会先把 URL 下载成 base64 再传。
> 所以对外用 `image_urls` 即可，函数内部会自动转换。

> **⚠️ 传 `model` 的同时，`createImageModel()` 必须固定传 `"hunyuan-image"`** ——
> 它不是模型名而是 **provider**，会拼进 URL。传错必 404。详见[第三节·补](#三补️-createimagemodel-的第一个参数是-provider不是模型名-2026-09-18-实测)。

**⚠️ 关于自动压缩的重要边界（实测澄清）**

压缩发生在**函数内部**，因此**救不了 HTTP 网关的 413** —— 网关在请求进入函数
**之前**就按 body 体积拒绝，函数根本没机会运行。

| 通道 | 大图（300KB+ base64）能否用 |
|---|---|
| HTTP 网关 `/api/gen-image` | ❌ 网关先 413，函数内压缩无效 |
| MCP（`?mcp=1`） | ❌ **同样走网关，一样 413**（实测 309KB base64 → 413） |

**结论**：**无论 HTTP 还是 MCP，参考图都优先用 `image_urls` 传 URL** ——
请求体只有几百字节，不受网关限制，且函数内会自动压缩。这是唯一优雅的路径。

## 三·补、⚠️ `createImageModel()` 的第一个参数是 **provider，不是模型名**（★ 2026-09-18 实测）

**这是本项目最大的一个坑，也是最容易搞错的一处。**

### 正确写法 vs 错误写法

```js
// ✅ 正确：provider 固定 "hunyuan-image"，模型名放 body
const imageModel = ai.createImageModel("hunyuan-image")
const res = await imageModel.generateImage({
  model: "HY-Image-3.0-Plus-4090-Tob-v1.0",   // ← 模型名在这里
  prompt: "...",
  size: "1024x1024",
  revise: { value: false },
})

// ❌ 错误：把模型名当成 provider 传进去 → 必 404
const imageModel = ai.createImageModel("HY-Image-3.0-Plus-4090-Tob-v1.0")
```

### 为什么？看源码

`node_modules/@cloudbase/ai/dist/cjs/models/image-model.js`（含内嵌原始 TS）：

```ts
private getGenerateUrl(subUrl: string) {
  return `${this.baseUrl}/${this.provider}/${subUrl}`   // ★ provider 被拼进 URL
}
```

```ts
public defaultGenerateImageSubUrl = 'images/ar/generations'

public generateImageSubUrlConfig: Record<string, Array<[RegExp, string]>> = {
  'hunyuan-image': [[/^hunyuan-image(-v[12](\..*)?)?$/, 'images/generations']],
}
```

`provider` 是**渠道/供应商标识**，会被直接拼进请求路径。传错就等于把 URL 写成了：

```
❌ .../HY-Image-3.0-Plus-4090-Tob-v1.0/images/ar/generations   ← 多了一层不存在的 provider 段
✅ .../hunyuan-image/images/generations
```

→ 服务端找不到那个 provider 段，**404**。

### 实测对照（同一份代码，只改 `createImageModel()` 的参数）

| `createImageModel(p)` | 请求体 `model` | 结果 |
|---|---|---|
| `p = "HY-Image-3.0-Plus-4090-Tob-v1.0"` ❌ | `HY-Image-3.0-Plus-4090-Tob-v1.0` | ❌ `404`（~133ms） |
| **`p = "hunyuan-image"`** ✅ | `HY-Image-3.0-Plus-4090-Tob-v1.0` | ✅ **成功**（8.6s，正常出图） |
| `p = "hunyuan-image"` ✅ | `hunyuan-image` | ✅ 成功（4.4s） |

### 关键推论

1. **`model` 字段本身是被服务端接受的** —— `HY-Image-3.0-Plus-4090-Tob-v1.0`
   在 provider 正确时**完全可用**，本环境**无需额外开通**。
2. **`generateImageSubUrlConfig` 只影响 `subUrl` 那一段**，且**不命中也有合法 fallback**
   （`images/ar/generations`）。所以「正则不匹配」**不会**导致 404 ——
   我之前据此推断「3.0 不支持」是**错的**。
3. **404 的真正来源**永远是 `provider` 拼错导致的**路径错误**。

### 判别指纹（重要）

| 状态码 | 含义 | 耗时量级 |
|---|---|---|
| **`404`** | **`provider` 传错** → 路径不存在 | ~130ms（服务端立即拒） |
| **`429`** | provider 正确、路由通过，仅**并发限流**（默认并发=1） | ~550ms |
| **`400`** | 参数/请求体问题（如 URL 传进 `images`） | 视情况 |
| **`200`** | 成功 | 4~9s |

**记住：`404` = provider 写错；`429` = 通了但被限流（等几秒重试即可）。**

## 六、当前函数能力

**入参**（HTTP 与 MCP 两个入口一致）：

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `prompt` | string | 必填 | 描述文本，**上限按模型动态判定**（3.0 → 8192；`hunyuan-image` → 500） |
| `size` | string | `1024x1024` | 4 种尺寸可选，**T2I / I2I 均支持** |
| `model` | string | `HY-Image-3.0-Plus-4090-Tob-v1.0` | 仅 T2I 有效；I2I 固定 `HY-Image-v3.0-I2I-ToB-v1.0.1` |
| **`footnote`** | string | — | **水印文字（≤16 字符）。三态见下表** |
| `seed` | number | — | 固定种子可复现（T2I / I2I 均已支持） |
| `images` | array | — | 图生图 **base64**（最多 1 张）。⚠️ 传 URL 会报 `url_in_images_field` |
| `image_urls` | array | — | 图生图 **URL**（**推荐**：请求体小、不受网关限制、函数内自动压缩） |
| `compress` | boolean | `true` | 参考图超 120KB 自动压到 768px JPEG |
| `revise` | object | T2I `{value:false}` / I2I `{value:true}` | prompt 改写 |
| `url` | string | — | `image_urls` 的单值简写 |

> **prompt 上限怎么算的**：`model === "hunyuan-image" ? 500 : 8192`。
> 默认（3.0）走 8192；显式传 `model:"hunyuan-image"` 才降回 500。
> 可用环境变量 `DEFAULT_MODEL` 覆盖默认模型，无需改代码。
> ⚠️ 代码里 `PROVIDER` 与模型名是两个独立常量 ——
> 曾因「同名多义常量」差点把 provider 改成模型名（详见[第三节·补](#三补️-createimagemodel-的第一个参数是-provider不是模型名-2026-09-18-实测)）。

### `footnote` 的三种取值（★ 重点）

| 取值 | 效果 | 返回体 |
|---|---|---|
| **不传** | 默认水印「AI生成」 | `footnote: null` |
| **传空白**（如 `" "`） | ✅ **水印不可见 = 事实上的无水印** | `footnote: " "`, `noWatermark: true` |
| 传文字（≤16 字符） | 替换为自定义水印 | `footnote: "你的文字"` |

> ★ **无水印的做法**：传 `footnote: " "`（一个空格）。
> SDK 没有独立的"关闭水印"开关，但空白字符串会让水印渲染不出来 ——
> 2026-09-18 实测确认：右下角区域边缘强度 0.30（空白）vs 2.17（文字），视觉上完全干净。
>
> 注意：传**空字符串 `""`** 会被判定为"未传"，回落默认水印；必须传**至少一个空格**。

| `strength` | 官方文档未定义，SDK 静默丢弃 |

| ~~`model=HY-Image-3.0-Plus-4090-Tob-v1.0`~~ | **❌ 已恢复支持**（v1.9.0）。当初误判为「公网 404」，真因是 provider 传错。现已是**默认模型** |

## 七、已知限制

1. **水印可以做到"不可见"** —— 传 `footnote: " "`（空白）即可，返回体 `noWatermark: true`。
   SDK 无独立开关，空白字符串是可行绕过法（已实测）。传文字则替换，不传则默认「AI生成」。
2. **并发数为 1** —— 连续调用可能触发上游异常，需间隔重试（约 5~8 秒）。
3. **图片 URL 24 小时失效** —— 需及时落盘或转存云存储。
4. ~~**3.0 模型公网不可用**~~ —— **❌ 此结论已推翻**（2026-09-18）。
   3.0 模型**完全可以公网调用，现已是默认模型**。
   当初误判为「不可用」，真因是 `createImageModel()` 传错了 provider（详见[第三节·补](#三补️-createimagemodel-的第一个参数是-provider不是模型名-2026-09-18-实测)）。
5. ~~**参数错误也返回 HTTP 200**~~ —— **❌ 已在 v2.0.0 修复**。
   现业务错误会透传正确状态码（400/422/500），详见[第十二节](#十二http-状态码约定v200-起统一透传)。
5. **HTTP 网关有 payload 上限（≈230KB）** —— 实测 309KB base64 请求返回
   `HTTP 413 EXCEED_MAX_PAYLOAD_SIZE`。**MCP 通道同样受限**（也走网关）。
   ⚠️ **这个限制在网关层，函数内压缩救不了**（请求进不来）。
   - ✅ **正确做法：参考图统一用 `image_urls` 传 URL**（请求体几百字节，不受限）
   - 若必须传 base64，需调用方自行压到 **768px JPEG q82**（约 65KB / base64 89KB）
6. **I2I 垫图最多 1 张** —— 官方限制，`images` / `image_urls` 二选一（`images` 优先）。
7. **I2I 返回的 `revised_prompt` 很长** —— 因 `revise` 默认开启，含 thinking 标签，
   属正常行为；如需精简可传 `revise:{value:false}`。
8. **`sharp` 依赖通过「云函数层（Layer）」提供** —— ✅ 已解决（详见第十节）。
   函数代码包**不含** `node_modules`，依赖全部由层挂载。
   若层未绑定，函数会自动降级为「原样透传」，并在返回体
   `compress.reason = "sharp_unavailable"` 中告知，**不会报错**。
9. **混元上游偶发抖动** —— 少量请求会返回 `FUNCTIONS_INVOCATION_FAILED`（v1.5.2 起
   T2I 分支已加 try/catch，会转为可读的 `success:false` + `errMsg`）。重试即可。

### 8.3 MCP（JSON-RPC）

入口加 `?mcp=1`，或带 header `x-mcp: 1`。

> ⚠️ **鉴权规则**：`initialize` / `tools/list` **不需要 key**（客户端握手）；
> **`tools/call` 必须带 key**，否则返回 JSON-RPC 错误 `-32001`。

```bash
# 1) 协议握手（无需 key）
curl -X POST "$API?mcp=1" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"my-client","version":"1.0"}}}'

# 2) 列出工具（无需 key）
curl -X POST "$API?mcp=1" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}'

# 3) 文生图（★ 必须带 key）
curl -X POST "$API?mcp=1" \
  -H "Content-Type: application/json" \
  -H "x-api-key: $KEY" \
  -d '{
    "jsonrpc": "2.0", "id": 3, "method": "tools/call",
    "params": { "name": "generate_image", "arguments": {
      "prompt": "一只戴宇航头盔的橘猫漂浮在星云中，电影感光照",
      "size": "1280x720",
      "footnote": " "
    }}
  }'

# 4) 图生图（URL 传参考图 + 尺寸，★ 必须带 key）
curl -X POST "$API?mcp=1" \
  -H "Content-Type: application/json" \
  -H "x-api-key: $KEY" \
  -d '{
    "jsonrpc": "2.0", "id": 4, "method": "tools/call",
    "params": { "name": "generate_image", "arguments": {
```

### 8.4 MCP 客户端配置示例

本函数是一个**远程 Streamable HTTP MCP Server**，任何支持远程 MCP 的客户端都能直接接。
先记住两个关键值：

| 项 | 值 |
|---|---|
| **Server URL** | `https://YOUR_ENV_ID-YOUR_APPID.ap-shanghai.app.tcloudbase.com/api/gen-image?mcp=1` |
| **鉴权 header** | `x-api-key: <你的 API_KEY>` |
| 传输类型 | `http`（Streamable HTTP） |

> ★ **URL 末尾的 `?mcp=1` 不能少** —— 它是本函数区分「MCP 模式」与「普通 HTTP 模式」的开关。
> 也支持用 header 替代：`x-mcp: 1`。

#### 8.4.1 通用 JSON 配置（Claude Desktop / Claude Code / Cursor / Cline 等）

绝大多数客户端读的都是同一个 `mcpServers` 结构：

```json
{
  "mcpServers": {
    "generateImage": {
      "type": "http",
      "url": "https://YOUR_ENV_ID-YOUR_APPID.ap-shanghai.app.tcloudbase.com/api/gen-image?mcp=1",
      "headers": {
        "x-api-key": "你的 API_KEY"
      }
    }
  }
}
```

> ⚠️ **`"type": "http"` 必须写**。有 `url` 但没有 `type` 的条目会被客户端当成 **stdio** 服务器，
> 报错：`MCP server "xxx" has a "url" but no "type"`。
> 部分客户端（遵循 MCP 规范原文）也接受别名 `"type": "streamable-http"`，两者等价。

> 💡 **别把 key 明文提交进 Git**。支持变量展开的客户端可以写成
> `"x-api-key": "${GEN_IMAGE_KEY}"`，key 放环境变量里。

配置文件位置（常见客户端）：

| 客户端 | 路径 |

| Claude Code（项目级） | 项目根目录 `.mcp.json` |

#### 8.4.4 自写客户端（Node，零依赖）

```js
// mcp-client.mjs —— 最小可用的 MCP 客户端
const URL = "https://YOUR_ENV_ID-YOUR_APPID.ap-shanghai.app.tcloudbase.com/api/gen-image?mcp=1"
const KEY = process.env.GEN_IMAGE_KEY

let id = 0
async function rpc(method, params) {
  const body = { jsonrpc: "2.0", method }
  // ★ 通知(notifications/*)不能带 id —— 带了会被当请求, 语义就错了
  if (!method.startsWith("notifications/")) body.id = ++id
  if (params !== undefined) body.params = params

  const r = await fetch(URL, {
    method: "POST",
    headers: { "Content-Type": "application/json", "Accept": "application/json, text/event-stream", "x-api-key": KEY },
    body: JSON.stringify(body),
  })
  return r.json()
}

// 1) 握手（不需要 key，但带上也无妨）
console.log(await rpc("initialize", {
  protocolVersion: "2024-11-05", capabilities: {}, clientInfo: { name: "my-client", version: "1.0" },
}))
// 2) 必需通知：告诉服务端握手完成
await rpc("notifications/initialized")
// 3) 列工具
console.log(await rpc("tools/list", {}))
// 4) 出图（★ 这一步才校验 key）
const res = await rpc("tools/call", {
  name: "generate_image",
  arguments: { prompt: "一只戴帽子的橘猫坐在窗台上，暖色阳光", size: "1280x720", footnote: " " },
})
console.log(JSON.parse(res.result.content[0].text))
```

#### 8.4.5 连接不上？按这个顺序查

| 症状 | 原因 | 改法 |
|---|---|---|
| 客户端报 `has a "url" but no "type"` | 漏了 `"type": "http"` | 补上。无 `type` 会被当 stdio |
| 握手阶段就失败 / 工具列表空 | 漏了 `?mcp=1`，请求走进了**普通 HTTP 模式**，返回的不是 JSON-RPC | URL 补 `?mcp=1`，或加 header `x-mcp: 1` |

| 偶发 `429` | 上游混元**并发=1** 限流 | 间隔 5~8 秒重试；这是上游限制，非配置问题 |

## 九、常见误用（踩坑清单）

按"报错信息 → 原因 → 改法"查。这几条都是实测踩过的，不是推测。

| 症状 | 原因 | 改法 |
|---|---|---|
| **`{"code":"INVALID_ENV"}`，任何路径都是** | **网关没匹配到路由** —— 最可能是路径写错。生产路径是 **`/api/gen-image`**，不是 `/api/generateImage` | 用 `queryGateway(action="listRoutes")` 核对真实路由；本环境只有 `/api/gen-image` 与 `/api/hello` |
| `400` + `Request failed with status code 400`，`compress.origBytes` 只有几百字节 | **把 URL 传进了 `images` 字段**。`images` 只接受 base64，模型拿 URL 当 base64 解码成垃圾 | 改用 `image_urls: ["https://..."]`。函数现在会直接返回 **HTTP 422** + `url_in_images_field` 提示 |
| `HTTP 413 EXCEED_MAX_PAYLOAD_SIZE` | 请求体超网关 ≈230KB（base64 原图 ×1.33） | 参考图改用 `image_urls` 传 URL（请求体几百字节）。**函数内压缩救不了，网关在函数之前就拦了** |
| 传了 `footnote` 但水印还是「AI生成」 | 传的是**空字符串** `""`，被判定为"未传" | 传**单个空格** `" "`（或任意纯空白）才会走"水印不可见"分支 |
| 传了 `strength` / `logoAdd` / `enable_thinking` 没反应，也不报错 | SDK 白名单过滤，未知字段**静默丢弃** | 别传。这三项 SDK 层不支持，只能绕过 SDK 直连裸 API |
| `success:false` + `FUNCTIONS_INVOCATION_FAILED`（偶发） | 混元上游限流/超时抖动（**并发数为 1**） | 间隔 5~8 秒重试。v1.5.2 起 T2I 分支也会返回可读 `errMsg`，不再崩成平台泛化错误 |
| `images` / `image_urls` 都传了 | `images` 优先级更高 | 只传一个。垫图**最多 1 张**（官方限制） |
| 拿到的图片 URL 第二天打不开 | 图片 URL **24 小时失效** | 及时落盘或转存云存储 |
| 返回的 `revised_prompt` 巨长、带 thinking 标签 | `revise` 默认开启（约 +30s） | 属正常行为；要精简就传 `revise: {value: false}` |
| **`404`（约 130ms 就返回）** | **`createImageModel()` 传了模型名** —— 它是 **provider**，会被拼进 URL，传错则路径不存在 | provider 固定传 **`"hunyuan-image"`**。模型名放请求体的 `model` 字段（本函数已内置处理） |
| **`429`** | provider 正确、路由已通，只是**并发限流**（默认并发=1） | 等 5~8 秒重试即可，**不是配置错误** |
| 参数错了却拿到 **HTTP 200** | v1.9.0 及之前的已知缺陷：业务错误返回普通对象，网关强制 200 | **升级到 v2.0.0**，现按 400/422/500 透传（详见[第十二节](#十二http-状态码约定v200-起统一透传)） |
| **MCP 客户端连不上，或工具列表是空的** | ① 漏了 `?mcp=1`（走进了普通 HTTP 模式，返回的不是 JSON-RPC）；② 漏了 `"type": "http"`（被当 stdio）；③ v2.0.0 及之前 `notifications/initialized` 被鉴权拦掉，标准客户端判定握手失败 | 见 [8.4.5 连接不上排查表](#845-连接不上按这个顺序查) |

## 十、sharp 依赖方案：云函数层（Layer）✅

### 10.1 为什么要用层

`sharp` 含**原生二进制**（`.node` + `libvips-cpp.so`），平台绑定。踩过的两个坑：

1. **CloudBase 代码包依赖缓存**：`updateFunctionCode` 的 `isWaitInstall`
   **只在函数首次创建时装依赖**，后续更新复用旧依赖缓存 —— 改代码也不重装。
2. **本地 node_modules 会被打包上传**：Windows 上 `npm install` 只拉
   `@img/sharp-win32-x64`，**缺** `@img/sharp-linux-x64`（云端要的就是这个）。

实测证据（解剖函数代码包）：包内条目 6147 条、`.node` 文件 **0 个**、
`@img/sharp-linux-x64` **缺失**、且 `sharp/package.json` 带 `src/*.cc` 源码
（说明是本地源码安装的产物）→ 云端 `require("sharp")` 必然抛错。

### 10.2 层信息

| 项 | 值 |
|---|---|
| 层名 | `sharp_YOUR_ENV_ID` |
| 版本 | `1` |
| 兼容运行时 | `Nodejs18.15`（与函数一致） |
| 内容 | `sharp@0.33.5` 的 **linux-x64** 完整依赖树（134 文件） |
| 体积 | 7.05 MB（压缩包），远低于 50MB 上限 |
| 关键文件 | `@img/sharp-linux-x64/lib/sharp-linux-x64.node`（269KB）<br>`@img/sharp-libvips-linux-x64/lib/libvips-cpp.so.42`（16.2MB） |

### 10.3 复现步骤（如需重建层）

```bash
#    { "dependencies": { "sharp": "^0.33.5" } }

#    期望：node_modules/@img/sharp-linux-x64/lib/sharp-linux-x64.node
```

- 层版本创建后不可修改，要更新只能建新版本（新版本号）

## 十一、API Key 鉴权（fail-closed，v1.8.0 引入）

### 11.0 为什么不用平台侧的权限控制（2026-09-18 查官方文档确认）

查过两条官方路径，**都不适用于本场景**：

| 方案 | 为什么不适用 |
|---|---|
| 网关 `enableAuth` | ① **全局开关**，会连带拦 `/api/hello` 与静态托管；② 校验的是 **CloudBase 身份 token**（有有效期、需换发），语义是「带 CloudBase 身份才能访问」，**不是**「带一串固定 key 才能访问」 |
| 云函数**安全规则**<br>（[官方文档](https://docs.cloudbase.net/cloud-function/security-rules)） | ① **仅对客户端 SDK 调用（`callFunction`）生效**，对 HTTP 网关访问**无效**（文档明确列出不适用场景：管理端 API、定时触发器、数据库触发器）；② 规则值只有 `true` / `false` / `"auth != null"` / `"auth.loginType != 'ANONYMOUS' && auth != null"`，**只能判「是否登录」，不支持比对固定密钥**；③ 配置是**环境级共享**的一份 JSON，无法只给单个函数设 key |

安全规则官方文档原文明确：

> **不支持**基于用户角色、用户组、特定用户 ID 等更复杂的权限控制。
> **如需更精细的权限控制，可以在云函数内部进行验证。**

**→ 本方案（函数内校验）正是官方推荐的路径。**

**两种机制的正确分工**：

| 调用方 | 该用什么 |
|---|---|
| 小程序 / Web SDK 的 `callFunction` | **安全规则**（`auth != null`） |
| HTTP 网关 / curl / 第三方自动化 | ★ **函数内 API Key**（本章） |
| 定时触发器 / 管理端 API | 两者均不适用 |

### 11.1 核心语义：fail-closed

**必须与环境变量 `API_KEY` 完全一致，否则拒绝。** 没有任何后门：

| `API_KEY` 状态 | HTTP 访问行为 |
|---|---|
| **未配置** | ★ **拒绝所有 HTTP 访问**（`server_misconfigured`）—— 不是放行 |
| 已配置 | 必须携带完全一致的 key，否则 401 |

> ⚠️ 与 v1.7.0 的**行为差异**：旧版「未配置就放行」，便于灰度；新版**未配置就全拒**，
> 避免「忘了配环境变量」导致接口裸奔。代价是环境变量被误删会直接中断服务。

**唯一例外**：**直接调用函数**（`invokeFunction` / 管理端 API / 定时触发）
不经 HTTP 网关，天然没有 headers，也无需校验 —— 判定依据是 event 里
是否存在 `httpMethod` / `headers` / `requestContext`。

### 11.2 四种传 key 方式（按优先级）

```
1. header  x-api-key: <key>              ← 推荐
2. header  Authorization: Bearer <key>
3. query   ?api_key=<key>                ← 浏览器/curl 快速测
4. body    { "api_key": "<key>", ... }
```

header 名大小写不敏感（`x-api-key` / `X-Api-Key` 都认）。

### 11.3 响应行为

被拒时返回**真正的 HTTP 401**（不是 200 带个错误码），body：

```json
{ "success": false, "code": "unauthorized", "message": "缺少 API Key。..." }
```

未配环境变量时：

```json
{ "success": false, "code": "server_misconfigured", "message": "服务端未配置 API_KEY 环境变量，已拒绝所有 HTTP 访问。..." }
```

> ⚠️ **实现要点（踩过的坑）**：CloudBase HTTP 网关只有收到
> `{ isBase64Encoded, statusCode, headers, body }` 这种结构才会透传状态码；
> 返回普通对象（哪怕带 `httpStatus: 401`）网关一律回 **200**，调用方按状态码
> 判断会误判成成功。已在 `unauthorizedResponse()` 里处理。

MCP 通道被拒时返回 JSON-RPC 错误：

```json
{ "jsonrpc": "2.0", "id": 3, "error": { "code": -32001, "message": "缺少 API Key。..." } }
```

### 11.4 MCP 通道的特殊处理

**判据：这个方法是否消耗我的后端额度 —— 不是「我有没有实现它」。**

| 方法 | 校验 key | 原因 |
|---|---|---|
| `initialize` | ❌ 放行 | 客户端探活/协商必需 |
| `notifications/initialized` | ❌ 放行 | ★ **协议必需的握手完成通知**（见下方踩坑） |
| `notifications/*`（cancelled / progress 等） | ❌ 放行 | 协议层通知，不消耗额度 |
| `ping` | ❌ 放行 | ★ 客户端探活必发，拦了会判定服务端异常 |
| `tools/list` | ❌ 放行 | 列工具，不消耗额度 |
| `logging/setLevel` | ❌ 放行 | 客户端设置日志级别 |
| `resources/*`、`prompts/*` | ❌ 放行 | 本 Server 不提供，但客户端可能试探；拦掉会被误认为鉴权失败 → 回标准 **-32601** |
| **未知方法**（拼错的） | ❌ 放行 | ★ 回 **-32601 Method not found**，**不是** `-32001` |
| `tools/call` | ✅ **校验** | 真正消耗混元额度 |

> ★ **2026-09-18 踩坑（v2.1.0 修复）**：最初只放行了 `initialize` / `tools/list`，
> 漏了 `notifications/*`。而 `notifications/initialized` 是 MCP 握手的**必需通知**
> （客户端握完手必发）、**没有 `id`**，一旦被拒 → 标准客户端判定握手失败 → **直接连不上**。
>
> ★ **v2.1.1 又修两处**（都是同一判据的延伸）：
> 1. **`ping` 被拦** —— 客户端探活会调，被拒会被判定"服务端异常"。
> 2. **拼错的 method 返回 `-32001`** —— 客户端会以为"key 不对"而去折腾凭证，
>    实际问题在方法名。改成：**MCP 通道里只有 `tools/call` 校验 key**，
>    其余一律放行、由 dispatch 回标准 `-32601`。
>
> ⚠️ **实现陷阱**：改「只有 `tools/call` 校验」时，若写成无条件的
> `if (method !== "tools/call") return null`，会把**普通 HTTP 请求**（此时 `method` 是 `null`）
> 也放行 → **所有 HTTP 接口免鉴权**。必须用 `isMcpContent` 把两个通道分开。
> 这个 bug 被单测「无 key → 401」当场抓出 —— 又一次印证**安全断言要正反都测**。
>
> **核心教训**：给 MCP Server 加鉴权时，**协议层方法要整体放行，不能只挑自己认识的那几个**。
> 判断依据应该是「这个方法是否消耗你的后端额度」，而不是「我有没有实现它」。

| MCP 方法 | 是否校验 | 说明 |
|---|---|---|
| `initialize` | ❌ 放行 | 客户端探活/协商必需 |
| `notifications/initialized` | ❌ 放行 | ★ **协议必需的握手完成通知**（见上方踩坑） |
| `notifications/*`（cancelled / progress 等） | ❌ 放行 | 协议层通知，不消耗额度 |
| `ping` | ❌ 放行 | 客户端探活必发（v2.1.1 补） |
| `tools/list` | ❌ 放行 | 列工具，不消耗额度 |
| `logging/setLevel` | ❌ 放行 | 客户端设置日志级别 |
| `resources/*`、`prompts/*` | ❌ 放行 | 本 Server 不提供 → 回标准 **-32601** |
| **未知方法**（拼错的） | ❌ 放行 | ★ 回 **-32601**，**不是** `-32001` |
| `tools/call` | ✅ **校验** | 真正消耗混元额度 |

这样 MCP 客户端能正常完成握手和工具发现，只有真正出图才要 key。
（注意：若 `API_KEY` **未配置**，则连握手也拒绝，见 11.1）

## 十二、HTTP 状态码约定（v2.0.0 起统一透传）

### 12.1 状态码表

| 状态码 | 语义 | 典型 `code` |
|---|---|---|
| **200** | 成功 | — |
| **400** | 调用方参数问题（可自行修复） | `invalid_param` |
| **401** | 鉴权失败 | `unauthorized` |
| **422** | 参数语法正确但语义不可用 | `url_in_images_field`、`download_failed` |
| **500** | 服务端异常 | `server_misconfigured` |

### 12.2 为什么需要这个（踩过的坑）

CloudBase HTTP 网关**只在返回特定结构时才透传状态码**：

```js
// ❌ 返回普通对象 -> 网关一律回 HTTP 200
return { code: "invalid_param", message: "prompt 最多 500 字符" }
//   调用方 res.status === 200，会以为出图成功了

// ✅ 必须返回这个结构
return {
  isBase64Encoded: false,
  statusCode: 400,
  headers: { "Content-Type": "application/json; charset=utf-8" },
  body: JSON.stringify({ success: false, code: "invalid_param", message: "..." }),
}
```

> 注意：body 里写 `httpStatus: 401` **无效** —— 那只是个普通字段，
> 网关不看它。必须用顶层 `statusCode`。

### 12.3 实现方式

代码里统一走两个函数，避免遗漏：

| 函数 | 作用 |
|---|---|
| `fail(code, message, extra)` | 构造业务失败结果（稳定带 `success:false` + `code`） |
| `httpify(result)` | 入口处统一包装：按 `ERROR_HTTP_STATUS` 映射表决定状态码 |

```js
const ERROR_HTTP_STATUS = {
  invalid_param: 400,
  url_in_images_field: 422,
  download_failed: 422,
  server_misconfigured: 500,
}
```

设计要点：
- **成功结果不被包裹**（保持原有 body 结构，向前兼容）
- **上游异常（无 `code`）不被误包装**（仍按 200 返回可读的 `errMsg`）
- **已带 `statusCode` 的不二次包装**（401 走 `unauthorizedResponse`）
- **未登记的错误码兜底 400**

### 12.4 MCP 通道不受影响

MCP 走 JSON-RPC，**HTTP 层恒为 200**，错误放在 `error.code`（如 `-32001`、`-32601`）。
这是 JSON-RPC 的规范行为，不要试图改。

## 十三、能脱离云函数跑吗

**能。** 2026-09-18 已在普通 Node 进程实测真实出图成功（4.5s）。完整说明见
[`selfhosted/README.md`](../selfhosted/README.md)，这里有可运行的 `server.js`。

### 唯一实质改动：显式传凭证

云函数里 SDK 从运行时环境变量自动读凭证；自建环境没有，必须显式传：

```js
// 推荐：服务端 API Key
cloudbase.init({ env: "your-env-id", accessKey: process.env.CLOUDBASE_APIKEY })

// 腾讯云长期密钥
cloudbase.init({ env: "your-env-id", secretId: "...", secretKey: "..." })

// 临时密钥 —— ★ 必须带 sessionToken，漏了会 401
cloudbase.init({ env: "your-env-id", secretId: "...", secretKey: "...", sessionToken: "..." })
```

### 与云函数版的差异（就这些）

| # | 差异 | 说明 |
|---|---|---|
| 1 | 凭证显式传入 | 唯一功能性改动 |
| 2 | 去掉"直接调用函数"放行路径 | 自建版所有请求都是 HTTP，该分支无意义 |
| 3 | 请求体上限 230KB → 8MB | 无网关限制 |
| 4 | `notifications/*` 返回 202 空体 | 云函数版返回 `result:null`（受网关约束） |
| 5 | 多 `/healthz` | 便于容器健康检查 |

其余逻辑（默认模型、prompt 上限、尺寸白名单、水印三态、状态码映射、压缩阈值）**逐字相同**。

### 注意

- **自建不能突破上游并发=1** —— 那是混元模型侧的限制，与跑在哪无关。
- `sharp` 装不上也不崩：`compress.reason` 返回 `sharp_unavailable`，图原样透传。
- 两版**可以并存**：云函数收轻量请求，自建版收大图请求，客户端按 URL 切换。
